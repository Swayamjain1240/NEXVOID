# v1.5.0 — the policy time machine (M21)

**Tag:** `v1.5.0` · **Milestone:** M21 · **Requirements:** FR-29, FR-30 · **ADR:** [0013](../adr/0013-temporal-revisions.md)

## What this release adds

An answer can now be asked **as of a date**, and it is built only from the revisions that were
in force on that date. Two new behaviours follow from that:

- `as_of=YYYY-MM-DD` on `GET /v1/ask` and `POST /v1/ask` (and `--as-of` on the CLI). Optional;
  absent means "now", so every existing client keeps its meaning.
- A refusal reason that did not exist before: **`not_yet_in_effect`**, with `effective_from`
  naming the day the revision that *does* answer the question takes effect. "I don't know" and
  "that rule does not exist yet" are different facts, and a policy assistant that conflates
  them is unusable at a counter.

## What changed underneath

| area | change |
|---|---|
| schema | `chunks.valid_from` / `chunks.valid_to` (ISO dates, `''` = unbounded); pre-M21 databases migrate in place |
| store | dated ingest **closes** the open revision the day before and appends its own; a back-dated ingest raises `InputError` instead of rewriting history |
| retrieval | the date mask is applied *inside* `BM25Index.search` and the cosine search, before fusion — an out-of-force chunk cannot occupy a candidate slot or collect a vote |
| answer | `as_of` plumbing, `not_yet_in_effect`, and a novelty vocabulary scoped to the revisions in force |
| api | `as_of` accepted and echoed; a malformed date is a `400 INPUT_INVALID`, never a quiet reinterpretation; citations carry `valid_from` / `valid_to` |
| cli | `ingest --effective`, per-file `doc@YYYY-MM-DD.md` names, `ask --as-of` |
| corpus | `corpus/temporal/` — six authored revisions of three policies, two each |
| eval | `make temporal`: `results/temporal.md` |

## What this release does not do

No large language model, no write API, no roles — unchanged from v1.4.0. The temporal history is
six authored revisions with assumed-known effective dates, and there is no transaction-time
axis: the system can say what a policy said in 2024, not what it told a user in 2024
(`docs/17-limitations.md`, L17–L18). The corpus revisions are synthetic, disclosed in the report
header and in the limitations register.

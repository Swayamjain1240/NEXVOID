# v1.7.0 — the saturation soak stops failing (M23)

**Tag:** `v1.7.0` · **Milestone:** M23 · **Requirements:** NFR-01, FR-20 · **Plan:** [18](../18-performance-plan.md)

## The result

| 10 unpaced users, 30 minutes | before (`v1.6.0`) | after |
|---|---:|---:|
| p95 | 58.40 ms | **22.88 ms** |
| p50 | 24.59 ms | 9.01 ms |
| p99 | 83.55 ms | 32.85 ms |
| sustained throughput | 349 rps | 910 rps |
| requests answered | 628,983 | 1,638,403 |
| failures | 0 | 0 |
| shed as `503 OVERLOADED` | — | 0 |

NFR-01 is written at 10 concurrent users with a 50 ms p95 target. It now holds for 30 minutes of
unpaced load, which is the stricter reading, and not only for a burst.

## Which change did it

Not the one this phase is named after, and the reports say so.

M22 halved service time (2.21×). At ~2 ms per request, ten clients keep about **one** request in
flight, so an admission limit of 32 never binds and the soak shed **nothing**. The committed
50-user burst sheds nothing either, so today the bound is exercised by `tests/test_admission.py`
and not by load at all. Claiming the queue fixed p95 would be a story the numbers do not support.

## What shipped

- `src/atlas/admission.py`: at most `max_inflight` (32) served at once, `max_waiting` (64) more may
  wait at most `admission_wait_ms` (25), the rest are refused immediately.
- `503 OVERLOADED` with `Retry-After: 1`, in the same error envelope as every other refusal (FR-23).
- `GET /v1/metrics` carries an `admission` block: `limit`, `queue_limit`, `wait_ms`, `inflight`,
  `waiting`, `admitted`, `rejected`, `reject_rate`. Shedding is visible, not inferred.
- **Liveness and metrics are never shed.** They are what an operator reaches for during an overload.
- The contract probe now requires that block, so capacity is part of the published surface.
- The load harness counts a shed request **apart** from a failure, and reports p95 over served
  traffic only. Counting a deliberate 503 as a failure would have reported this phase as a
  regression; counting it as a success would have hidden the load the server declined.

## A bug the tests caught

The first implementation applied the queue bound *before* checking for a free slot, so
`queue_limit=0` refused requests on an idle server. The queue bound is a limit on **waiting**: a
free slot must never consult it. `test_the_limit_bounds_concurrency` fails on that version.

## What it does not change

The frozen sets: recall@10 0.9167, refusal 1.0000, temporal 9/9 with 0 future leaks, determinism 0
differences, contract 15/15. No threshold, ranking rule or refusal decision was touched — this phase
adds a capacity bound on the request path.

## Carried forward

`docs/17` L3 now states the real limit: shedding has only been seen in a burst, so a workload
holding more than 32 concurrent slow requests is measured nowhere. L8 keeps the fairness gap: the
bound is global and first-come, so one client can occupy every slot. `docs/18` M24 (worker
processes) is next.

# v1.10.0 — growing the index without rebuilding it (M26)

**Tag:** `v1.10.0` · **Milestones:** M26 · **Requirements:** NFR-03, FR-01..FR-03 · **Plan:** [18](../18-performance-plan.md)

## What shipped

An ingest no longer invalidates the tenant view. `HybridIndex.refresh(tenant_id)` compares the
store's document signature against the one the view was built from and returns what it did:

| result | when |
|---|---|
| `extend` | chunks were added: postings, vector rows, token caches and ranker features are appended, existing vectors reused |
| `rebuild` | a chunk's text or revision window changed, or a chunk disappeared — none of those can be patched into a posting list |
| `none` | the store has not moved since the view was built |
| `missing` | no view exists yet, so the next query builds one |

SQLite now runs in WAL mode, so an ingest in another process does not block the serving process,
and `ATLAS_RELOAD_MS` (default 1000, 0 disables) is how often a serving process checks — one
cheap signature query per interval per tenant, never per request.

## Measured

`results/scale.md`, `python -m bench.scale`:

| chunks | cold start | warm query p50 | rebuild | append 5 documents |
|---|---:|---:|---:|---:|
| 34 | 66.7 ms | 0.11 ms | 67.0 ms | 27.1 ms |
| 1,053 | 1,761 ms | 3.93 ms | 1,755 ms | 43.8 ms |
| 10,053 | 13,912 ms | 33.11 ms | 14,770 ms | 545 ms |

At 10k chunks an append costs **545 ms against a 14,770 ms rebuild (27.1×)**, and a warm query
33.11 ms. Query cost grows 301× for 296× the chunks: the exact scan is linear, as predicted, and
at 33 ms it is not the bottleneck this project's NFRs name — so the plan's non-goal stands and no
ANN index was added. Cold start remains the expensive number, paid once per process per tenant.

The 1k and 10k corpora are generated text over a 300-word vocabulary. They are a cost
measurement, not a quality claim; quality stays on the frozen sets, unchanged.

## What it does not change

Frozen sets: recall@10 0.9167, refusal 1.0000, temporal 9/9 with 0 leaks, determinism 0
differences, contract 15/15. The retrieval path itself is untouched — `bench/perf.py` still shows
the same two arms and the same ratio.

## Carried forward

L21: the append is an approximation for the dense half — hashed TF-IDF bakes corpus idf into each
row, so appending leaves the old rows on the previous idf. One mini-corpus equivalence test
(`tests/test_incremental.py`) shows the ranking unchanged; that is not a proof, and a revision or
deletion still rebuilds. L19 gained a note: a same-code re-run during this phase read 1.55–1.65×
slower on the pure pipeline with the same ratio, so cross-session absolute numbers are not
comparable and the committed load reports were not replaced by a slower session's run.
`docs/18` M27 (query expansion for FR-17) is the last phase.

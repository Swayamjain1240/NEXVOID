# NEXVOID — a knowledge assistant that cites its sources or refuses to answer

**For reviewers, recruiters and hiring managers.** The engineering README is [`README.md`](README.md);
this page is the two-minute version, written for someone who will not read the code.

**Status:** complete, tagged `v1.4` · 20 milestones · 87 commits · 15 release tags · Python, single
node, no containers. (The Python package is still named `atlas`; NEXVOID is the project name.)

---

## What it is, in one paragraph

NEXVOID is a question-answering service for an organisation's own documents — policies, handbooks,
circulars. A user asks a question in plain English and gets back **the exact sentence from the
document that answers it, with a citation**, or an explicit **"I don't know."** It never writes its
own prose, so it cannot invent a policy that does not exist. That choice is the whole design: for
policy questions, a confident wrong answer is worse than no answer.

## The four numbers worth remembering

| | result |
|---|---|
| **Retrieval quality** — does it find the right document? | recall@10 **0.9583** (best config) on a hand-labelled 24-question set |
| **Latency** — is it fast enough to use? | p95 **19.56 ms** over 15 minutes at 10 concurrent users, 0 failed requests |
| **Safety** — can it be abused? | **40/40** prompt-injection attacks refused · **0** cross-organisation data leaks across 12 probes |
| **Reproducibility** — do the numbers hold? | a clean clone reproduces them exactly (**PASS**); two identical runs produce **0 differences** |

Every number above is regenerated by a command in the repository and stored in a committed report.
None of them is an estimate.

## What makes this project different from a tutorial RAG demo

Most "RAG project" repositories show a chatbot working once. This one is built around **proving what
it does**, and — more unusually — **recording what it fails to do**.

1. **Every claim has a receipt.** 23 committed reports in `results/`, each stamped with the machine,
   corpus size, encoder and git commit that produced it, plus the command to regenerate it. If a
   number is not in a report, it is not claimed.
2. **A real ablation, not a vibe.** Five configurations × two embedding models, one change per row,
   each with a 95% confidence interval — which is how the project *proved* the reranker was the
   bottleneck instead of guessing it.
3. **Holdouts that were allowed to fail.** Two question sets were written before the results were
   seen, and the refusal gate **collapsed from 1.0000 to 0.1667** out of sample. That failure was
   published, not tuned away, and then partly recovered with a second, independent signal
   (0.1667 → 0.3333 and 0.5000 → 0.6667 without rejecting a single answerable question).
4. **The line between "measured" and "believed" is drawn in public.** `docs/17-limitations.md` lists
   16 gaps with their evidence, including the ones that make the product look worse.
5. **The quality gate was demonstrated failing on purpose**, so CI is a control rather than a claim.

## Engineering summary

- **Stack:** Python 3, standard-library HTTP server, SQLite, NumPy — 2,628 lines of source across 71
  files, one runtime dependency, no framework, no Docker, no cloud services. It runs offline on a
  laptop.
- **Architecture:** parse → structure-aware chunking → dual index (BM25 keyword + dense vector) →
  reciprocal-rank fusion → confidence gate → extractive answer with passage citations. Tenant data is
  partitioned in SQLite.
- **Quality engineering:** 149 automated tests; a module-size ceiling of 200 lines enforced by script;
  architecture layer rules verified against the real import graph; a requirement-traceability test
  that fails if any of the 48 requirement IDs lacks a test, report or recorded exemption;
  a CI pipeline (lint → size ceiling → tests → corpus gate → evaluation gate).
- **Operations:** structured logs with redaction (0 raw personal values in 133 audited lines), a
  circuit breaker with degraded-mode answers (3/3 verified), per-route metrics with a 1,000-request
  latency window, a request-level timing waterfall, and a generated dashboard built from the reports.
- **Documentation:** 12 architecture decision records, each naming the alternative it rejected and the
  measurement behind the choice; 17 design documents; a handover runbook; a release note per tag.

## Notable engineering decisions I would happily defend in an interview

- **Refusing to adopt my own work.** A trained reranker scored 0.90 held-out against 1.00 for the
  existing retriever, so it was **not shipped** — the weights are committed, marked unadopted, and the
  loader refuses to use them.
- **Leaving a threshold where the evidence put it.** When the refusal gate failed out of sample, the
  obvious move was to retune the threshold on the new questions. That would have destroyed the
  holdout, so theta was left alone and the failure was reported instead.
- **Naming an unmeetable requirement instead of gaming it.** One requirement asks hybrid retrieval to
  never score worse than its best component. With a perfect dense retriever that is provably
  equivalent to copying it — so the requirement was formally amended to a measurable form, with the
  proof committed.
- **Publishing the number that fails the target.** Under 30 minutes of unpaced load, p95 is 58.40 ms
  against a 50 ms target. That reading sits next to the target, above the passing one.

## What it does not do

Honestly, because this is the part most portfolios omit: no large language model (answers are
extracted, not generated), no document upload API (ingestion is a command-line operation), no roles
beyond a single shared token, no rate limiting, no TLS, no multi-node deployment, and no backup
story. The test corpus is 18 documents, so the absolute scores will not transfer to a real corpus
unchanged. All sixteen items are itemised with evidence in
[`docs/17-limitations.md`](docs/17-limitations.md).

## Verify it in two minutes

```bash
git clone https://github.com/Swayamjain1240/Model-1 && cd Model-1
python -m venv .venv && ./.venv/Scripts/activate      # Windows; use .venv/bin/activate elsewhere
pip install -e . && make test                          # 149 tests
python -m atlas.cli serve                              # then open http://127.0.0.1:8070/
```

To reproduce a measurement rather than run the tests: `make eval`, then open
`results/eval_report.md` — the header states the corpus, encoder, commit and command.
